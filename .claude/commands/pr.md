현재 브랜치의 변경사항으로 Pull Request를 만드세요.

## 순서

1. 아래를 병렬로 실행해 브랜치 상태를 파악한다:
   - `git status`
   - 현재 브랜치가 원격 브랜치를 추적 중인지, push가 필요한지 확인
   - `git log [base-branch]...HEAD` — base 브랜치(보통 `main`)에서 갈라진 이후의 전체 커밋 로그
   - `git diff [base-branch]...HEAD` — 전체 변경 내용
   - `gh issue list --state open` — 열려있는 이슈 목록
2. **연관된 이슈를 찾는다.**
   - 먼저 현재 브랜치 이름이 `{숫자}-...` 패턴(`/work`로 만든 브랜치)인지 확인한다. 맞으면 그 숫자를 이슈 번호로 우선 사용하고, `gh issue view {번호}`로 실제 존재하는 이슈인지만 검증한다 — 검색 단계를 건너뛴다.
   - 브랜치 이름에 번호가 없으면, 커밋 메시지·diff 내용을 열려있는 이슈 목록과 비교해서 관련 이슈를 찾는다.
   - 그래도 못 찾았으면 추측으로 아무 이슈나 연결하지 않는다 — 사용자에게 "이 PR에 대응하는 이슈 번호가 있는지, 없으면 이슈 없이 진행할지" 먼저 물어본다. 이슈가 있어야 할 만한 작업인데 없다면 `/issue`로 먼저 만들 것을 제안한다.
3. **최신 커밋 하나만이 아니라, PR에 포함될 모든 커밋과 diff 전체**를 실제로 읽고 분석한다. 커밋 메시지만 나열하지 말고, diff에서 무엇이 실제로 바뀌었는지 확인한다.
   - 제목: 70자 이내, 무엇을 바꿨는지 간결하게
   - 본문은 `.github/pull_request_template.md`의 섹션 구조(`## Summary`, `## Changes`, `## Test plan`, `## 관련 이슈`)를 그대로 따른다. 파일이 있으면 반드시 읽고 그 구조를 채운다 — 임의로 다른 구조를 쓰지 않는다.
   - `## Summary`: 커밋별 요약이 아니라 "무엇을, 왜" 관점에서 3~6개 불릿. 새로 생긴 파일/삭제된 파일/핵심 로직 변경은 파일 경로와 함께 구체적으로 언급
   - `## Changes`: 변경 파일이 5개 넘거나 여러 영역에 걸치면 작성, 아니면 섹션째로 생략
   - `## Test plan`: "검토했는지" 수준의 뭉뚱그린 체크박스 금지. diff 내용에 실제로 대응하는 구체적 항목만 작성 — 예를 들어 새 스크립트를 추가했다면 "`node scripts/x.js` 실행해서 y 출력 확인", 훅을 추가했다면 "규칙 위반 커밋 시도 → 막히는지 확인" 처럼 실행 가능한 명령/시나리오 단위로. 이미 이 세션에서 실행하고 결과를 확인한 테스트가 있으면 "완료"로 표시하고 결과를 한 줄로 남긴다.
   - `## 관련 이슈`: 이 섹션은 생략하지 않는다. 이슈 번호가 있으면 `Closes #123` (머지 시 이슈 자동 종료) 또는 `Refs #123` (관련은 있지만 이 PR로 끝나지 않는 경우) 형식으로 적는다. 2번 단계에서 이슈 없이 진행하기로 확인받았으면 "관련 이슈 없음 (사유: ...)"라고 명시적으로 적는다.
4. 원격에 push가 필요하면 사용자에게 먼저 알리고 진행한다 (`git push -u origin <branch>`).
5. `gh pr create --title "..." --body "$(cat <<'EOF' ... EOF)"` 형식으로 PR을 생성한다.
6. 생성된 PR URL을 사용자에게 알려준다.

## 주의사항

- base 브랜치(`main`)에는 직접 push하지 않는다.
- force push는 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- PR 생성은 되돌리기 어려운 공개 행동이므로, push/PR 생성 전에 항상 변경 요약을 보여주고 진행 여부를 확인받는다.
- 이미 열려있는 PR이 있는지 `gh pr list`로 먼저 확인한다. 있으면 새로 만들지 않고, 대신 내용을 위 기준으로 다시 작성해 `gh pr edit --body "..."`로 갱신할지 사용자에게 물어본다.
