사용자가 설명한 작업($ARGUMENTS)을 이슈부터 PR까지 끝까지 진행하세요.

전체 흐름: 이슈 확인/생성 → 브랜치 생성 → 구현 → 커밋(반복) → 완료 판단 → PR 생성.
이 중 **이슈 생성, push, PR 생성**은 공개적으로 남거나 되돌리기 번거로운 지점이라 확인을 받는다. 그 사이 구현과 커밋 반복은 매번 멈춰서 묻지 않고 진행한다 — 이게 이 명령어를 쓰는 이유다.

## 0단계 — 사전 점검 + 이전 브랜치 정리

1. `git status`로 현재 브랜치에 처리 안 된 변경사항이 있는지 확인한다. 있으면 사용자에게 먼저 알리고, 커밋해서 정리할지 그대로 두고 진행할지 물어본다.
2. `git checkout main && git pull`로 base 브랜치를 최신화한다 (충돌 등 문제가 있으면 진행을 멈추고 사용자에게 알린다).
3. `git branch --merged main`으로 이미 main에 머지된 로컬 브랜치를 찾는다. `main`/`master` 자신은 제외하고, `{숫자}-슬러그` 패턴(=`/work`로 만들었던 브랜치)만 대상으로 한다.
   - 해당하는 브랜치가 있으면 각각 `git branch -d {브랜치명}`으로 로컬 브랜치를 삭제한다.
   - 원격에도 같은 이름의 브랜치가 남아있으면 (`git ls-remote --heads origin {브랜치명}`로 확인) `git push origin --delete {브랜치명}`으로 같이 삭제한다.
   - 삭제 전 사용자에게 다시 묻지 않는다 — 이미 main에 머지된 게 확인된 브랜치만 대상이라 안전하다. 삭제한 브랜치 목록은 짧게 알려준다.
   - `--merged` 판단이 애매하거나(예: `-d`가 "not fully merged" 오류를 낸다) 확신이 안 서면 강제 삭제(`-D`)로 밀어붙이지 않고 그 브랜치는 건드리지 않은 채 사용자에게 알린다.

## 1단계 — 이슈 확보 (확인 필요)

1. `gh issue list`로 이 작업과 겹치는 이슈가 이미 있는지 확인한다.
   - 있으면 그 번호를 그대로 쓴다 (새로 만들지 않는다).
   - 없으면 `.claude/commands/issue.md`와 동일한 기준(배경/상세 내용/완료 조건)으로 제목·본문 초안을 작성해 **사용자에게 보여주고 확인받은 뒤** `gh issue create`로 생성한다.
2. 이슈의 "완료 조건"을 이 작업이 끝났다고 판단할 기준으로 기억해둔다 — 4단계에서 다시 쓴다.

## 2단계 — 브랜치 생성

1. 브랜치 이름을 `{이슈번호}-{영문-슬러그}` 형식으로 만든다 (예: 이슈 #12 "장바구니 Redis 연동" → `12-cart-redis`).
2. `git checkout -b {브랜치명}`으로 전환한다.
3. "이슈 #{번호} 확보, `{브랜치명}` 브랜치로 전환, 지금부터 구현 시작합니다"라고 짧게 알리고 바로 3단계로 넘어간다 (여기서 진행 여부를 다시 묻지 않는다).

## 3단계 — 구현 + 커밋 반복 (확인 없이 진행)

1. 이슈 내용을 논리적 작업 단위로 나눈다 (예: 엔티티 → 서비스 → 컨트롤러, 혹은 기능 A → 기능 B).
2. 각 단위마다:
   - 코드를 작성/수정한다.
   - 관련 파일만 `git add`한다 (`-A` 금지는 기존과 동일).
   - `.claude/commands/commit.md`의 메시지 컨벤션(`{type}: {제목}`, `feat/fix/refactor/docs/test/chore`, 72자 이내, 왜 했는지 드러나게)을 따라 커밋 메시지를 작성하고 커밋한다.
   - `.husky/pre-commit`·`commit-msg` 훅이 실패하면 원인을 고치고 같은 단위 안에서 재시도한다 (사용자에게 매번 물어보지 않는다 — 진짜 판단이 필요한 애매한 상황일 때만 멈추고 질문한다).
   - **이 단계에서는 스테이징 파일 확인이나 push 여부를 매번 묻지 않는다.** push는 5단계에서 한 번만 처리한다.
3. 막히는 지점(요구사항이 애매함, 테스트 실패 원인이 불명확함, 기존 설계와 충돌)이 생기면 추측으로 밀어붙이지 않고 멈춰서 사용자에게 질문한다.

## 4단계 — 완료 판단

1. 1단계에서 기록해둔 이슈의 "완료 조건"을 하나씩 확인한다.
2. 관련 테스트/스크립트가 있으면 실행해서 통과를 확인한다.
3. 완료 조건을 다 만족하면 5단계로 진행한다. 일부만 됐으면 사용자에게 현재까지 진행 상황을 요약하고, 계속할지/여기서 PR을 만들지(예: 작업이 커서 나눠서 리뷰받고 싶은 경우) 물어본다.

## 5단계 — PR 생성 (확인 필요)

`.claude/commands/pr.md`의 순서를 그대로 따른다: 브랜치 이름에서 이슈 번호 자동 인식 → `.github/pull_request_template.md` 구조로 본문 작성(Summary/Changes/Test plan/관련 이슈에 `Closes #{번호}`) → **push 여부 확인** → `gh pr create` → PR URL 안내.

## 하지 않는 것

- 이슈 생성, push, PR 생성은 확인 없이 진행하지 않는다.
- `main`에서 직접 작업하지 않는다 — 항상 2단계에서 만든 브랜치에서만 작업한다.
- 완료 조건을 확인하지 않고 임의로 "다 됐다"고 판단해 PR을 만들지 않는다.
- 구현 중 막히는 지점을 추측으로 덮지 않는다 — 애매하면 멈추고 묻는다.
