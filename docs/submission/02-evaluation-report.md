# 평가 리포트 — 지표 · 개선 전후 · 실패 원인 분석

측정 환경은 두 종류이며 각 수치에 **환경을 명시**한다. 무료 티어(로컬/Render)라 절대 수치보다 **개선 전후 비교와 재현 가능한 pass/fail**에 무게를 둔다.

- **Render 배포**: 0.1 vCPU + 네트워크. "실환경" 병목 진단·개선의 근거(결정 31).
- **로컬 loopback**: Docker PostgreSQL/Redis + 백엔드 동일 머신. 회귀 게이트(thresholds) pass/fail과 정확성 검증에 사용. k6·앱 자기간섭으로 절대 처리량은 과대평가되므로 "게이트 통과 여부"로만 해석.

---

## 1. 성능 병목 진단 (before/after) — 핵심 지표

`GET /orders/lookup`(캐싱·락 없는 순수 DB 조회)에서 VU를 올려도 처리량이 정체하고 p95만 치솟는 **포화 패턴**을 발견하고, 추측이 아니라 **가설-검증-반증**으로 원인을 좁혔다.

| VU | 처리량(req/s) | p95 |
|---|---|---|
| 10 | 32.5 | 509ms |
| 20 | 34.5 | 1.38s |
| 30 | 42.6 | 1.69s |

(Render 0.1 vCPU. VU가 3배인데 처리량은 거의 그대로 → 포화)

**가설 검증 과정**
1. **DB 커넥션 풀 부족?** → `DB_POOL_MAX` 10→20 A/B. VU30에서 42.6→35.5로 오히려 악화 → **반증**.
2. **쿼리 자체가 느림?** → Supabase에 `EXPLAIN ANALYZE` 직접 실행. 0.479ms, JOIN은 "never executed" → **반증**.
3. **비교 테스트**: 같은 VU로 `/health`(단순 조회)는 47→79→101 req/s로 비례 증가, `/orders/lookup`만 정체 → 전역 CPU 부족이 아니라 **라우트별 처리 비용 차이**.
4. **원인 특정**: TypeORM이 매 요청 4개 엔티티(orders→order_items→product_options→products) 관계를 조립하는 **애플리케이션 레벨 CPU 비용**. 0.1 vCPU에서 누적돼 병목.

**개선**: `lookupOrder()`를 "존재 확인(단순 쿼리) → 존재할 때만 관계 조회" 2단계로 분리.

| 지표 (VU30, Render) | before | after | 개선 |
|---|---|---|---|
| 처리량 | 42.6 req/s | **68.4 req/s** | **+60%** |
| p95 | 1.69s | **1.05s** | **−38%** |

> **한계 인지**: TypeORM 쿼리 빌더 비용인지 검증 파이프라인 등 다른 요소인지 더 쪼개려면 유료 APM이 필요 — 블랙박스 k6로 확인 가능한 범위까지가 여기다.

## 2. 부하 테스트 재현 (fresh run, 2026-08-25, 로컬)

k6 스크립트는 저장소 `k6/`에 있고 thresholds로 **pass/fail 자동 판정**한다.

### 2-1. 처리량 회귀 게이트 — `k6/throughput-test.js`
```bash
k6 run -e VUS=10 -e DURATION=20s k6/throughput-test.js
```
thresholds: `p(95)<300ms`, 서버 오류율 `<1%` (404는 정상 응답으로 간주).

| 지표 | 결과 | 판정 |
|---|---|---|
| p95 | **11.42ms** | ✓ `p(95)<300` |
| 처리량 | 22,222 req / 20s ≈ **1,070 req/s** | — |
| 오류율(5xx/예외) | **0.00%** | ✓ `rate<0.01` |
| checks | 22,222 / 22,222 (100%) | ✓ |

→ **thresholds 모두 통과.** (로컬 loopback이라 절대 처리량은 Render와 비교 불가 — 이 실행의 의미는 "회귀 게이트가 초록"임을 재현 가능하게 보인 것)

### 2-2. 동시성 정확성 — `k6/order-concurrency.js` (핵심 정확성 지표)
재고 1개 옵션에 10 VU가 동시에 주문:
```bash
k6 run -e PRODUCT_OPTION_ID=1 -e VUS=10 k6/order-concurrency.js
```

| 지표 | 결과 |
|---|---|
| 주문 성공(201) | **1건** |
| 재고 부족(409) | **9건** |
| 최종 `product_options.stock` | **0** |
| 실제 생성된 `order_items` | **1건** |
| checks | 10/10 (100%) |

→ **초과 판매 0건.** 비관적 락이 의도대로 동작함을 결정적으로(deterministic) 증명. 이 결과는 반복 실행해도 동일하다(§5 재현성).

## 3. 안정성 방어 장치

"실제에 준하는 이상 상황"을 방어하고 그 근거를 테스트로 남겼다.

| 위협/실패 | 방어 | 근거 |
|---|---|---|
| **재고 초과 판매** | 비관적 락 + 트랜잭션 | k6 동시성 테스트(위 2-2) |
| **이상 입력** | class-validator DTO — 이메일 정규화, 전화번호 형식/정규화, 우편번호 5자리, 페이지네이션 상한(`@Max(100)`) | 유닛/e2e |
| **결제 중복·네트워크 실패** | 10초 타임아웃 + 5xx/네트워크 재시도(백오프) + `Idempotency-Key` + `ALREADY_PROCESSED` 멱등 + confirm 트랜잭션 락 | `payments.service.spec` |
| **유령 재고(결제 이탈)** | 방치 PENDING 만료 회수(재고 반납 + EXPIRED), 취소 시 재고 복원 | e2e(재고 1개로 회수 증명) |
| **계정 열거/브루트포스** | 로그인 타이밍 균일화(더미 해시 compare) + 로그인/가입 rate limit(10회/60초) | `auth.service.spec` |
| **권한 우회** | role 기반 `AdminGuard`(매 요청 DB 확인) + SSE 1회용 단기 티켓 | `admin.guard.spec` |
| **롤백 데이터가 UI에 노출** | SSE 이벤트는 트랜잭션 커밋 후에만 발행 | 설계 |
| **민감정보 로그 노출** | 로그에서 쿼리스트링 제거(PII·티켓 마스킹) | 결정 41 |
| **배포 환경 크래시** | CI e2e가 `AppModule` 실부팅으로 엔티티/부팅 오류 검출 | 결정 27 |

**실제로 발견해 고친 버그(정직한 기록)**
- 이메일 대소문자 불일치로 존재하는 주문이 404 → 정규화(결정 26)
- `payment_key`를 유니온 타입으로 선언 → TypeORM 오인식으로 배포 크래시 루프 → CI로 재현·수정(결정 27)
- Supabase 클라이언트를 생성자에서 즉시 생성 → 관련 env 없는 환경에서 부팅 크래시 → 지연 생성으로 수정
- 주문 취소가 재고를 복원하지 않던 잠재 버그 → 만료 회수와 공용 루틴으로 통합 수정(결정 45)
- **(오늘 발견)** k6 `order-concurrency.js`가 구 주소 스키마로 작성돼 현재 DTO 검증에 400 → 스크립트를 구조화 주소로 갱신

## 4. 테스트 커버리지

| 종류 | 개수 | 방식 |
|---|---|---|
| 유닛 테스트 | **105** | Repository/DataSource/Redis/fetch 모킹, 비즈니스 로직 검증 |
| e2e 테스트 | **17** | 실제 `AppModule` + 진짜 DB/Redis 부팅(TossPayments만 fetch mock) |

- e2e는 "주문 생성 → 재고 확인 → 결제 승인 → SHIPPED → 배송 단계 → DELIVERED → 조회"의 **풀 라이프사이클**과 회원가입~로그아웃, 장바구니 병합, 마이페이지 소유권(404), 만료 회수를 실 DB로 검증.
- **CI**(GitHub Actions): PR마다 typecheck → lint → 유닛 → e2e + 마이그레이션 실행까지 자동. (2026-08-25 기준 유닛 105 / e2e 17 통과)

## 5. 재현성

| 항목 | 보장 방법 |
|---|---|
| 환경 | `docker compose up -d` 한 줄로 PostgreSQL/Redis 동일 재현 |
| 스키마 | TypeORM 마이그레이션(멱등적) + 부팅 시 `migrationsRun` 자동 적용 → 로컬/CI/프로덕션 동일 |
| 테스트 | CI가 매 PR에서 동일 순서로 실행, 결과 일정 |
| **동시성 결과** | `order-concurrency.js`는 **결정적** — 재고 1개로 리셋 후 실행하면 항상 성공 1/충돌 9/재고 0 |
| 성능 게이트 | `throughput-test.js` thresholds로 pass/fail 재현 |

> **재현 시 주의(정직한 기록)**: 만료 회수(결정 45)가 오래된 PENDING의 재고를 되돌리므로, 동시성 테스트는 **깨끗한 상태(대상 옵션 재고=1, 잔여 PENDING 없음)에서 시작**해야 결정적이다. 실제로 오늘 첫 실행에서 잔여 PENDING이 회수돼 결과가 흔들린 것을 발견하고, 상태를 리셋한 뒤 재현했다. 이 상호작용 자체를 리포트에 남긴다.
